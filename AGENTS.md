# AGENTS.md

Use Context7 for current library and API documentation. Read the repository-root
`AGENTS.local.md` when present for the private Codex workflow.

Gitter is a native macOS Git client (SwiftUI, AppKit where SwiftUI falls short) that runs every git action through `/usr/bin/git`. macOS 26+, Apple silicon, Xcode 27, Swift 6 with complete strict concurrency. `docs/DEVELOPMENT.md` is the long-form reference (design decisions and their reasons, every test helper, the file-by-file layout, the debug harness); `docs/GUIDE.md` is what the app promises users, including its Safety section.

## Commands

`Gitter.xcodeproj` is generated by XcodeGen from `project.yml` and is git-ignored: run `xcodegen generate` after adding or removing files or changing `project.yml`.

The Tree-sitter packages are resolved once, with the network, into `.build/SourcePackages` (again only when a pin in `Syntax/Package.swift` changes):

```sh
xcodegen generate && xcodebuild -resolvePackageDependencies -project Gitter.xcodeproj -scheme Gitter -clonedSourcePackagesDirPath .build/SourcePackages
```

Every build and test after that runs offline: always pass `-clonedSourcePackagesDirPath .build/SourcePackages -disableAutomaticPackageResolution`, and run tests with `GIT_ALLOW_PROTOCOL=file GIT_SSH_COMMAND=/usr/bin/false GIT_TERMINAL_PROMPT=0`.

```sh
# Build (Debug)
xcodegen generate && xcodebuild -project Gitter.xcodeproj -scheme Gitter -configuration Debug \
  -derivedDataPath .build/DerivedData -clonedSourcePackagesDirPath .build/SourcePackages \
  -disableAutomaticPackageResolution build

# GitCore tests (swift test at parallel width 8; extra args go to swift test)
bash scripts/test-gitcore.sh
bash scripts/test-gitcore.sh --filter StashRecordTests        # one suite or test

# All three test targets (GitCoreTests, GitterTests, GitterSyntaxTests) through the scheme
xcodegen generate && GIT_ALLOW_PROTOCOL=file GIT_SSH_COMMAND=/usr/bin/false GIT_TERMINAL_PROMPT=0 \
  xcodebuild -project Gitter.xcodeproj -scheme Gitter -configuration Debug \
  -clonedSourcePackagesDirPath .build/SourcePackages -disableAutomaticPackageResolution -scmProvider system test
# one app suite: add  -only-testing:GitterTests/ResolverStoreTests
```

There is no linter. A change counts as finished when it passes these checks, which `docs/DEVELOPMENT.md` lists under "The gates":
- both test commands above pass;
- a Release build has zero compiler warnings;
- after the tests, the app's preferences (`dev.penzin.Gitter`) and `~/Library/Logs/Gitter` are unchanged;
- `GitCore/Sources/GitCore/ProcessRunner.swift` is unchanged against tag `v0.2.0`;
- no planning files are tracked.

The DMG is built by `scripts/package.sh` from a clean tree. `scripts/package-selftest.sh` tests that script's refusals.

## Known issues are deliberate

Both suites report "known issues" (`withKnownIssue`). They are negative controls: each one proves that an assertion helper *can* fail. A helper once silently passed everything because of a bug, and these controls exist to catch that. Never "fix" or delete them.

Note the known-issue count for each suite before your change. A different count afterwards needs an explanation. `docs/DEVELOPMENT.md` › Tests lists them all, and the totals written there may trail the real ones.

## Architecture

There are three code units, wired together in `project.yml`:

**`GitCore/`**, a SwiftPM package with no SwiftUI:
- It is the git layer.
- Twelve backend protocols define each area's contract: `GitBackend` (reads), plus working copy, branch, remote, stash, conflict, operation, history, tag, remote admin, compare and worktree.
- One implementation, `CLIGitBackend`, is split into `CLIGitBackend+<Area>.swift` files. It spawns git through `ProcessRunner`, which is frozen; `ProcessRunner+Streaming.swift` handles long network calls with progress and cancel.
- `Parsers/` reads git's own output into `Models/`.
- `PatchBuilder` builds the patches that staging and discards apply with `git apply --cached`. Gitter never writes the index itself.
- `GraphLayout` computes the lane graph in one pass in commit order.
- `CommandLog` is the sink that every git call reports to, and it feeds the diagnostics log.
- `GitCoreTestSupport` holds the test helpers both test targets share. It must never depend on GitCore, or Xcode links a second static copy of GitCore into the app's test bundle.

**`Syntax/`** (the `GitterSyntax` product):
- It wraps Tree-sitter: language detection, one highlighter per language, and `SyntaxKind`. Nothing outside it imports the binding.
- Every package is pinned `exact:` and no `Package.resolved` is committed.
- Some newer grammar versions break under Xcode, so a pin is never raised without building and running the app again. The reasons are in DEVELOPMENT.md › Syntax colours.

**`Gitter/`**, the app:
- **Windows and stores.** Each window has its own `@Observable @MainActor RepositoryStore`, made through `WindowRegistry`, which routes every open. The store owns that window's selection, snapshot, sheets, network lane, mutation state and fetch schedule.
- **Store extensions.** Behaviour lives in `RepositoryStore+<Area>.swift` extensions, one per feature area, for example `+Resolver`, `+DraftGuard`, `+Depth` and `+Refresh`.
- **Refresh.** `RepositoryWatcher` (FSEvents, debounced) triggers it.
- **Quitting.** It goes through `QuitFlow` and then `QuitGuard`, which checks every window. A window that is still writing hides instead of closing (`WindowCloseProxy`).
- **UI text.** Every sentence the UI shows lives in a `*Wording` type (`ConflictWording`, `RemoteWording`, `StashWording`, …), and GitterTests pin that wording and the decisions made from it. Put new UI text there, not inline in views.
- **Views.** `Views/` holds SwiftUI views and sheets. `Resolver/` is the Resolve Conflicts editor: three TextKit 2 columns, with `ResolverDocument` as the in-memory Result that is written once.

## Safety model (the product's core promise)

Gitter never discards work or commits without a confirmation that names what will be lost. Preserve these existing mechanisms:
- A discard records a stash entry first, and untracked files go to the Trash.
- A branch is deleted with `branch -d` first; `-D` runs only from the warning that `-d` opened.
- A pull is a fetch followed by a merge or rebase, never `git pull`.
- A force push is always leased on an explicit sha.
- A history action or a destructive housekeeping action shows its plan on a sheet, re-reads the plan just before git runs, and refuses if anything changed.

GitCoreTests includes a test that greps GitCore's sources for forbidden force flags.

## Rules learned the hard way

These rules come from real defects found during earlier milestones.

**Git config can add behaviour that loses work.** Production code reads the user's git configuration on purpose; that is what makes their remotes, signing and hooks work.
- Options like `fetch.prune`, `push.followTags`, `rebase.autoStash` / `updateRefs` and `merge.autoStash` turn plain commands into ones that lose work. Five loss paths so far came from configuration, none from flags.
- For every new git invocation, ask which config keys change its behaviour, and pass the explicit negative flag or refuse. GitCore already does this with `--no-prune`, `--no-autostash`, `--no-update-refs`, `--no-follow-tags` and `--no-recurse-submodules`.
- Diffs that are parsed always pin `--no-ext-diff --no-textconv --submodule=short --src-prefix=a/ --dst-prefix=b/`.

**Flags that are never used.**
- No force flag in GitCore except a leased `--force-with-lease=` inside a complete push vector (a scanner test enforces this).
- Never `--unidiff-zero`.

**A confirmation sheet is a snapshot.** The repository can change while it is open. Carry what the sheet showed (ids, tips, counts) into the mutation and verify it again there.

**Measure git; don't recall it.**
- Before relying on how git behaves (in code, a test or a design note), check it with real git in a `mktemp -d` repository.
- When measuring whether git refuses something during an operation, resolve and stage the conflicts first. Unmerged entries make git refuse everything, so the measurement proves nothing.

**Assertions must be able to fail.**
- A "nothing changed" helper must fail on an empty baseline.
- Every new assertion helper gets a `withKnownIssue` control that proves it can fail.
- A UI "nothing happened" check needs a positive control that proves the input actually landed.

**Concurrency and processes.**
- Never call `Process.waitUntilExit` across an `await`. After the `await`, the code resumes on another thread and waits on a run loop that nobody runs, so the hosted test hung. Use `waitForExit` from `GitCoreTestSupport`.
- Run the whole scheme test, not only `swift test`, because some failures appear only under the hosted xcodebuild run.

**Test host and AppKit.** Under the GitterTests host, `UserDefaults.standard` is the user's real `dev.penzin.Gitter` domain. Anything AppKit autosaves (split views, window frames) must have no autosave name when `TestHost.isRunningTests` is true. The per-test `.leavesTheRealDefaultsAlone` trait catches violations.

**Dependencies.** Tree-sitter, for syntax colours only, is the one approved third-party dependency. Everything else stays dependency-free.

## Tests

Tests use Swift Testing and run **real git in throwaway repositories**, never fakes, and never touch the user's repositories, git configuration, defaults or log:
- **GitCoreTests** clears the inherited `GIT_CONFIG_*` and `GIT_SSH_COMMAND` variables and sets `GIT_CONFIG_GLOBAL=/dev/null`. Remote tests use local bare repositories.
- **GitterTests** is hosted by the app (`TestHost`), so no repository is reopened and no automatic fetch starts:
  - Every git call runs under `TestGitEnvironment.isolated`.
  - Build stores with `makeTestStore`, which gives each test a scratch defaults suite, and repositories with `ScratchRepo`.
  - Wait with `waitUntilIdle` and `CallUnderTest`, not sleeps or wall-clock bounds.
  - `TestBackend` forwards every backend call to real git and can hook, fail or hold any one call (named by `TestBackend.Call`).

## Running the real app

Debug builds include launch hooks (`DebugLaunchHooks*.swift` and `HarnessControls.swift`, all `#if DEBUG`). They drive the UI from `GITTER_DEBUG_*` environment variables:
- select files, commits or lines;
- click and type;
- run branch and network steps;
- take snapshots of the window (`GITTER_DEBUG_SNAPSHOT_DIR`).

Any `GITTER_DEBUG_*` variable turns on the launch guard. The app then acts only on the repository named by `GITTER_DEBUG_OPEN`, and refuses and quits otherwise.

A scripted launch must:
- use a scratch repository;
- set `GITTER_LOG_DIR` to a scratch folder;
- pass `-ApplePersistenceIgnoreState YES`;
- export the `dev.penzin.Gitter` defaults before the run and restore them exactly afterwards.

Before and during a launch:
- **Quit the installed Gitter first.** An installed `/Applications/Gitter.app` shares the bundle id.
- **Launch the built binary directly.** `open -a` drops the environment.
- **Launch only after the build has finished.** A build still in progress or being re-signed crashes in dyld and puts a dialog on the user's screen.
- **Never share a `-derivedDataPath`** between concurrent xcodebuilds.
- **Take screenshots with the `snapshot:` step only,** which captures just the window. Never take a full-screen capture.

The harness cannot activate the app or open real context menus. Focus, key-window, tooltip and right-click behaviour can only be checked by a person with a real pointer.

The full variable and step reference is in DEVELOPMENT.md › Debug launch hooks.

## Repository conventions

- `docs/superpowers/`, `docs/BACKLOG.md` and `.superpowers/` are private working notes (specs, plans, the backlog). They are git-ignored and are never committed or linked from tracked files.
- Commit messages are one long descriptive sentence saying what changed and why (see `git log`). Work happens on `feature/*` branches and is merged to `main` through pull requests.
- The version is `MARKETING_VERSION` in `project.yml` plus the "(version X)" in `README.md`. A release is a GitHub release tagged `vX.Y.Z` with the notarized DMG attached. The in-app update check reads the latest release.
- `scripts/package.sh` refuses a tree that has any untracked file. A local-only file must be excluded (for example in `.git/info/exclude`) before packaging.
- Shipped milestones and the roadmap are under "Status / roadmap" in `docs/DEVELOPMENT.md`.
